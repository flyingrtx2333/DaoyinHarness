# File edit observation and delivery

Cloud Agent file tools return actual content-change receipts, independently of the model's interpretation. `file_read` includes the SHA-256 digest of the complete bytes from which its line window was produced. `file_write` and both `file_patch` forms return `mutation.changed`, before/after digests, affected ranges and a bounded changed-region preview. A preview is not a minimal diff or correctness verdict. Binary content has hashes without a text preview. No-op writes do not create a new verification hint.

The cloud capability adapter records successful read/write observations for the current run and injects version guards; the model does not reproduce hashes or receive a new input parameter. Existing targets must have an observation. New files use an absence guard. The executor checks versions under its existing workspace queue, with workspace processes paused. An unread existing target or a changed digest rejects the edit before writing and asks the model to read again. Unified patches inspect actual Git target paths, including rename/copy sources, before applying. Manual account resource APIs retain optional guards for compatibility; this policy is an Agent capability policy, not additional account consent.

Exact replacements reject empty or ambiguous context and use an atomic replacement preserving file ownership/mode. Observations require regular files up to 16 MiB. Unified patches address at most 128 files with at most 32 MiB of baseline bytes and a conservative per-file growth bound; receipts show at most eight files, at most 2000 preview characters each, with explicit omissions. Symlinks are not edit baselines. Successful operations refresh only the returned file versions; omitted targets require a fresh read before a subsequent edit.

New actual mutations renew the existing bounded delivery reminder. Targets are coalesced per resource. The kernel does not infer acceptance from file reads, inspect programming languages, mandate a test command, or add a separate verification state machine. Continuous editing may be followed by one focused verification. Syntax, types, tests and business checks belong to the mounted capability and actual user task. All calls still consume the original shared budget, and missing evidence must be reported accurately.

Real validation: `scripts/verify-file-edits-live.mjs --run --expected-revision <exact deployed commit>` uses ordinary account credentials through hidden stdin and three actual cloud Agent/tool/storage scenarios. It never supplies canned model replies or fabricated business responses. Static checks and deployment do not prove model behavior. Results, usage and official SWE grading are recorded separately.
