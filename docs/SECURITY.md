# DaoyinHarness Security Model

> Status: v1 security requirements. Implementations may strengthen these controls but may not weaken them without an ADR.

## 1. Trust boundaries

DaoyinHarness handles four different trust levels:

1. **Trusted local runtime code** distributed by Daoyin.
2. **Authenticated local browser UI** served by the runtime.
3. **Untrusted project and external content** generated by models, uploaded by users or fetched from the web.
4. **Remote services** including Daoyin OAuth and the AI Gateway.

Generated code, webpage text, documents, model output, memory content and tool output are data. None may alter policy or grant permission merely by containing instructions.

## 2. Loopback server

- Bind only to `127.0.0.1` and optionally `::1` when the same security behavior is verified.
- Reject unexpected `Host`, forwarded-host and proxy headers.
- Accept browser API requests only from the selected loopback origin.
- Use an opaque HttpOnly SameSite session cookie and CSRF token.
- Set restrictive CSP, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and frame restrictions on the control UI.
- Do not expose local filesystem paths, environment variables or stack traces in client errors.
- Generate a new local session secret per process and never accept it in a query parameter.

LAN access and remote control are not v1 features. They require a separate threat model and cannot be enabled through an undocumented flag.

## 3. Workspace confinement

Every file operation must:

1. start from a server-selected project root;
2. reject absolute, UNC, device and drive-relative user paths;
3. normalize path separators and reject `..` traversal;
4. resolve existing parents and symlinks/junctions to real paths;
5. verify the resolved path remains beneath the project root;
6. recheck the destination immediately before mutation;
7. use an atomic write pattern and bounded file size.

Windows alternate data streams, reserved device names and reparse-point escapes require explicit tests. Archive extraction validates every member before writing and enforces total-size and file-count limits.

## 4. Process and package execution

v1 has no arbitrary Shell tool. The implemented Process Service accepts an executable plus argument array from a runtime-owned named-operation policy; model input never supplies raw shell text or arbitrary argv. Current automatic operations are bounded read-only runtime/Git inspections. Workspace package scripts are a separate policy class because `package.json` scripts execute workspace-controlled code.

Implemented controls:

- working directory is workspace-relative, resolved through `realpath`, and must remain beneath the selected canonical root;
- only a minimal environment is inherited; Git credential prompts/pagers are disabled and `GIT_CEILING_DIRECTORIES` prevents repository discovery above the selected workspace;
- Git diff inspection disables external diff/textconv helpers and fsmonitor where applicable;
- execution uses `shell:false`, bounded argv/count, cancellation, timeout and bounded stdout/stderr evidence;
- package scripts require both a runtime allowlist match and a declaration in the safe workspace `package.json`;
- package-script execution requires an exact one-shot permission fingerprint scoped to account + resource + session;
- permission approval is append-only local state and cannot be granted by the model; approval does not itself start execution;
- successful process evidence explicitly reports `osIsolation: "none"` until a real OS sandbox provider exists.

Still required before describing process execution as sandboxed: OS-level filesystem/process isolation, explicit child-process/CPU/resource ceilings and enforceable per-operation network isolation. A future sandbox provider must sit below the current Process Service/permission contract rather than introducing a second command path.

## 5. Tool permissions

Tool permissions are evaluated by deterministic policy before execution. The model cannot approve its own request.

v1 categories:

- **read**: workspace read, glob, search and metadata;
- **write**: bounded workspace create/edit/delete through checkpoint-aware operations;
- **network**: HTTPS search/fetch through allowlisted clients and size/time limits;
- **browser**: isolated browser context for inspection and preview checks;
- **process**: named package, build, test and preview commands;
- **credential**: internal-only Cloud Client operations, never model-callable.

High-impact changes display the exact scope to the user. Current Process Permission grants are intentionally narrower than a remembered policy class: they bind the exact command fingerprint to the current account/resource/session and are consumed once. Broader remembered permissions require a separate policy design and are not part of the current implementation.

## 6. Preview isolation

Generated applications are untrusted, even when produced by the Agent.

- Serve previews on a distinct loopback port or origin from the control UI.
- Embed them in a sandboxed iframe without `allow-same-origin` unless a test requires and documents it.
- Do not expose control-session cookies to the preview origin.
- Block preview access to local runtime APIs by Origin and authentication checks.
- Apply resource, request and lifetime limits to preview processes.
- Report console errors and failed required routes as evidence; never inject control credentials for convenience.

## 7. Secrets and privacy

- Model-provider secrets exist only in the Daoyin cloud.
- OAuth refresh tokens use the OS credential manager; access tokens remain in memory.
- Redact authorization headers, cookies, passwords, API keys, OAuth codes, PKCE verifiers and recognized secret patterns before logs or model context.
- Transcript tool evidence stores hashes or opaque artifact references when raw content contains secrets.
- Logs have size retention limits and a user-visible export action that performs a second redaction pass.
- The model request includes only files and memory selected for the current task, not the whole home directory or unrelated projects.

## 8. External content and networking

- Fetch only `http` and `https`; block file, data, localhost, link-local, private-network and cloud-metadata targets unless the operation is a declared local preview check.
- Re-resolve DNS at connection time and defend against redirects into blocked ranges.
- Enforce response size, content type, redirect count and timeout limits.
- Page content, metadata and attached documents are marked untrusted in model context.
- Search failure does not prevent direct inspection of a user-supplied valid URL.
- Screenshot capture and artifact storage are separate stages with separate error codes.

## 9. Updates and distribution

- The internal npm beta and future public package use a protected scope and provenance-enabled CI publication.
- Published contents are allowlisted; source maps, credentials, local reference material and test secrets are excluded.
- The CLI reports its exact version in health and diagnostics.
- Automatic self-update is not a v1 feature. A future updater requires signature/integrity verification and rollback.

## 10. Security acceptance

Security tests must cover loopback exposure, Host/Origin/CSRF, OAuth replay, workspace traversal, symlink/junction escape, archive bombs, command injection, preview-origin isolation, secret redaction, SSRF and cancellation of child processes.

A security policy violation may be shown as critical. Ordinary build, model, storage or network failures use normal warning/error presentation and an Agent-authored summary.
